## 1. Идентификаторы — решение по фактическому коду

**Что уже есть в проекте:**

| Где | Поле | Что это |
|---|---|---|
| профиль `data.items[uid]` | ключ `uid` | **экземпляр предмета** — GUID (`HttpService:GenerateGUID`), глобально уникален |
| профиль `data.items[uid].id` | `id` | **ItemID** — вид, ключ `Config/Items` (`"GoldenThrone"`) |
| `ItemRegistry` Entry | `uid`, `itemId`, `state`, `owner`, `slot`, `carrier`, `thief`, `part`, `boss`, `bossSlot` | состояние экземпляра на сервере |
| `TheftLedger` Theft | `thief`, `owner`, `uid`, `slot`, `event`, `stage`, `startedAt` | кража конкретного uid |
| журнал §6 Entry | `id` (= transferId), `uid`, `from`, `record`, `at` | передача конкретного uid |
| метки | `transfersOut[transferId]`, `transfersIn[transferId]` = `{ uid, at }` | у жертвы и у вора |

**Решение [Т]:**
- **Идентичность этажа — это `uid` экземпляра.** При краже `DataService.TransferItem` переносит запись под тем же
  `uid` (`to.items[uid] = copy`). Журнал, метки и `TheftLedger` уже отслеживают именно `uid`.
  - Отдельный FloorID не нужен: он дублировал бы `uid` и требовал бы своей синхронизации.
- **Ключ уникальности внутри башни одного владельца — `id` (ItemID).** Это безопасно: он ограничивает только
  одновременное наличие (у владельца не больше одного этажа данного вида). Глобальной идентичностью он не служит —
  одинаковые ItemID у разных игроков — это разные `uid`.
- **FloorIndex не хранится в записи.** Это позиция `uid` в `data.tower.order`, она меняется при сдвиге. `uid` при
  этом не меняется никогда.

**Почему этаж — не новое `place`.** `Shared/Inventory.Normalize` при каждой загрузке переводит любое `place`, кроме
`slot` и `storage`, в `storage` (`Inventory.luau:84`). Поэтому у этажа `place` остаётся `"storage"`, а признак этажа —
новое поле `builtAt`.
- Плюс для отката: если режим башни выключить, этажи просто окажутся предметами в инвентаре. Ничего не теряется,
  `Inventory.Normalize` не меняется.

### 1.1 Структуры данных

```lua
-- Профиль: запись экземпляра (существующие поля + одно новое)
data.items["9f1c…-uid"] = {
	id = "GoldenThrone", -- ItemID
	mods = {}, place = "storage", rot = 0, -- как сейчас; у этажа place всегда "storage"
	acquiredAt = 1795000000, source = "boss", boss = 2, -- как сейчас
	from = nil, pending = nil, -- как сейчас: только у украденного / пока передача не подтверждена
	builtAt = 1795000500, -- НОВОЕ [Т]: есть число → запись является этажом владельца
}
-- Профиль: порядок этажей (НОВОЕ [Т], создаётся только в режиме башни)
data.tower = { v = 1, order = { "9f1c…-uid", "a2b4…-uid" } } -- снизу вверх; FloorIndex = номер в списке
data.migration = { tower = { v = 1, at = 1795000000 } } -- отметка миграции v5 → v6 (только тестовые копии)

-- Реестр: новое состояние и индекс
Entry.state = "Floor" -- с полями owner, itemId; FloorIndex реестр не хранит
floorIndex[owner][itemId] = uid -- второй Floor того же itemId у владельца — отказ перехода

-- Модель этажа (сервер, реплицируется): Plots.Plot_<n>.Tower.Floors["F_" .. uid]
-- атрибуты: Uid, ItemId, Index, BaseY, State ("Building" | "Built" | "Pending" | "Transfer")
```

**Инварианты** — их держит `TowerRules.Normalize` при каждой загрузке, проверяет Lune:
1. `order` содержит только `uid` записей с `builtAt` и без `pending`, без повторов.
2. Каждая запись с `builtAt` есть в `order`; недостающие дописываются наверх по `builtAt`.
3. В `order` не больше одного `uid` на один `id`. Лишним (выше) снимается `builtAt` — они становятся повторами.
4. Запись с неизвестным `id`, `income == 0` или `legacy` — без `builtAt`. Этажом она не будет и повтором не считается.
5. **Повтор** = запись без `builtAt`, чей `id` уже есть в `order`. Это вычисляемое свойство, не поле.

### 1.2 Жизненный цикл экземпляра

| Событие | Профиль | Реестр | Башня |
|---|---|---|---|
| 1. Постройка (B) | `builtAt = now`, `uid` в конец `order` — один кадр | Stored → Floor, `floorIndex[owner][id] = uid` | модель `F_<uid>` наверху, `State = Building` 2 с → `Built` |
| 2. Получен дубликат | новая запись (новый `uid`, без `builtAt`) — `InventoryService`, как сейчас | Stored | ничего; в окне — «Повтор» |
| 3. Кража (E): начало и снятие | без изменений | Floor → Lifting → Stolen; `floorIndex` держится — у жертвы нельзя построить такой же | `State = Pending`: каркас, экспоната нет, дохода нет |
| 4. Неудачная доставка (E) | без изменений | Stolen → Floor | `State = Built`, экспонат на место |
| 5. Успешная доставка (E) | журнал (запись с `builtAt = now`, если у вора нет этажа этого `id`, иначе без) → один кадр: `TransferItem` + `uid` из `order` жертвы + в `order` вора → подтверждение | у жертвы: снят из `floorIndex`; у вора: Floor (или Stored, если повтор) | жертва: удаление и сдвиг; вор: этаж наверх (`State = Transfer`, без дохода, пока есть `pending`) |
| 6. Продажа дубликата (D) | `items[uid] = nil` + монеты — один кадр; второй запрос записи не находит | новое `ItemRegistry.Remove(uid, "sold")` — только из Stored | ничего |
| 7. Повторный вход | `Release` сохраняет; при входе: `ResolveTransfers` → `Inventory.Normalize` → `TowerRules.Normalize` | `Restore` как Stored → для `uid` из `order` → Floor | `LoadTower` строит по `order` |

**Сбои:**
- **Сбои кражи** (падение до журнала, после журнала, после шага 2 с сохранением жертвы и без него, DataStore
  недоступен, повторная доставка) решаются, как сейчас для экспонатов: `TransferJournal.Resolve` по меткам. При сбое
  на шаге 5 запись вора с `pending` даёт этаж в состоянии `Transfer` без дохода. Если вход решит `drop`, запись удаляется, а `Normalize` убирает `uid` из `order`. Если `grant` — запись
  приходит из журнала с `builtAt`, и `Normalize` ставит этаж наверх (или делает повтором).
- **Устойчиво у двух владельцев экземпляр быть не может.** Решение принимается только по меткам `transfersOut` и
  `transfersIn`, `TransferJournal` не меняется.

## 2. Несколько игроков на разных этажах — коллизии и интерьеры

**Решение: у каждого построенного этажа серверный каркас существует всегда.** Глобального ActiveFloor и
включения столкновений по требованию нет.

**Почему без включения по требованию.** Своего персонажа в Roblox просчитывает клиент.
- Сервер мог бы создать пол этажа за мгновение до телепорта, но пакет с полом приходит к клиенту позже. Персонаж
  упал бы сквозь ещё не дошедший пол — то же при задержке сети и при двух игроках.
- Постоянный каркас убирает весь этот класс ошибок. Цена — около 10 деталей на этаж (§3).

### 2.1 Что строит сервер — `World/TowerBuilder`
- **Холл** (≈ 25 деталей на башню): пол, стены, проём входа (место двери D37), шахта лифта одной деталью на всю
  высоту, точка сдачи (сундук участка остаётся тем же `plot.chest`).
- **Каркас этажа** — невидимые (`Transparency = 1`) детали с `CanCollide`, `CanQuery`:
  - плита пола 1;
  - наружные стены 4–8 (проёмы балконов — разрывы);
  - тумба экспоната 1;
  - крупные массы темы, через которые нельзя проходить, — до 4.
- **Экспонат** — `ItemFactory`: хитбокс + меш, 2 детали; надпись «+X/сек».
- **Точки** — Attachment на плите, без новых деталей:
  - подсказка «Лифт»;
  - 4 места высадки;
  - позже — точки подсказок кражи и защиты (E).
- Всего ≈ 10 деталей на этаж. Устройства защиты (E) — дети модели своего этажа: едут вместе с ним при сдвиге.
- Все проверки сервера (расстояние, видимость экспоната, путь вора через лазер, «внутри этажа») идут только по
  серверным деталям. Убранства клиента на сервере нет вовсе, поэтому отключённая или не загруженная декорация ничего
  не открывает.

### 2.2 Что рисует клиент — `TowerController`
Клиент рисует всё видимое: стены с окнами, архитектуру темы, свет, эффекты. Детали убранства — `Anchored`,
`CanCollide = false`, `CanQuery = false`, `CanTouch = false`, в папке только у клиента `workspace.TowerDecor`.

**Чтобы вид не расходился с полом:** модуль темы описывает `shell` (серверные коробки) и `decor` в одних
координатах этажа. Lune `check_tower` проверяет:
- каждая видимая стена темы стоит на месте стены каркаса (±0.2);
- пол убранства лежит на плите;
- площадка лифта 8 × 8 пуста.

**Какой этаж показывать.** Клиент берёт `ItemId` из атрибута модели `F_<uid>` и тему — из `Floors.Get(ItemId)`.
Темы нет — `Floors.Placeholder`.

**Нужен ли интерьер.** Раз в 0.25 с клиент обходит этажи по кругу (≤ 40 за такт):
- `myIndex` = этаж персонажа по высоте, если он стоит в контуре этой башни; считается без лучей.
- **LOD 0 — интерьер:** персонаж в этой башне и `|Index − myIndex| ≤ 1`, или камера ближе 45 стад к центру этажа.
- **LOD 1 — фасад:** центр этажа ближе 250 стад к камере.
- **LOD 2 — силуэт:** ближе 600 стад.
- **Дальше** ничего не строится.
- **Гистерезис:** уровень покидается только на 110 % порога, чтобы на границе не мигало.

**Загрузка и выгрузка:**
- Очередь сборки — не больше `Tower.BuildPartsPerFrame` (250) деталей за кадр. LOD 0 цели лифта и своего этажа идёт
  первым.
- Готовая модель кешируется по (`uid`, LOD). LOD 0 выгружается через 5 с после того, как перестал быть нужным: при
  быстрой езде на лифте интерьер не пересобирается.
- Если очередь уже заняла кадр, LOD 2 дальних башен не строится.

**Лифт с точки зрения клиента:**
1. `ElevatorGo` уходит на сервер.
2. Клиент сразу ставит LOD 0 этажа-цели первым в очередь и затемняет экран на 0.3 с.
3. Сервер переносит персонажа на постоянный пол, поэтому падения нет даже без декора.
4. Затемнение снимается, когда LOD 0 собран, но не позже 1 с.

**Перестройка башни:**
- клиент слушает `Floors.ChildAdded` / `ChildRemoved` и `AttributeChanged` (`Index`, `BaseY`, `State`) у `F_<uid>`;
- общий счётчик — `Tower:GetAttribute("Version")`;
- при смене `BaseY` убранство плавно едет за 1 с со старой высоты на новую.

**Украденный этаж:**
- `State = Pending` — клиент меняет интерьер и фасад на вариант «каркас с лесами».
- `F_<uid>` удалён — убранство уничтожается, этажи выше едут вниз.
- `State = Transfer` (у вора) — обычный вид с меткой «Передаётся…».

### 2.3 Несколько игроков одновременно (пример из ТЗ)
- **Игроки на этажах 3, 20, 40.** Каркасы всех трёх стоят всегда. Каждый клиент сам выбирает свой LOD 0, сервер про
  интерьеры ничего не знает.
- **Вор на 40-м.** Удержание и проверки идут по серверному каркасу 40-го этажа (E).
- **Четвёртый в лифте.** Перенос на места высадки по кругу: 4 места, занятые в последние 2 с пропускаются, поэтому
  двое не встают в одну точку.
- **Владелец ставит защиту (E).** Устройство — серверная деталь на плите этажа; площадка лифта запрещена.

### 2.4 Сдвиг после удаления среднего этажа
В одном кадре сервера:
1. Удаляется `F_<uid>`.
2. Персонажи на этажах выше переносятся `MoveGuard.Teleport` на ту же точку −20 — **раньше полов**.
3. Модели этажей выше переносятся `PivotTo` вниз на 20.
4. Обновляются `Index`, `BaseY`, `Version`.

Изменения одного кадра уходят клиенту одним шагом репликации: персонаж и пол приходят вместе, падения нет. Тест
проверяет луч вниз под каждым сдвинутым игроком через 0.2, 0.5 и 1 с.

## Приложение A. Цены продажи повторов — предложение [?], не утверждено

**Формула:** продажа = 0.5 × средняя цена поимки Бумом = 0.5 × (цена набора / 3) / базовый шанс редкости.
- Так продажа всегда дешевле добычи.
- `доход × 60` дал бы бесконечные деньги: Epic «Скелет тираннозавра» продавался бы за 12K при поимке ≈ 1.1K.

**Примеры:**

| Предмет | Редкость | Цена продажи |
|---|---|---:|
| «Голова моаи» | Common | 280 |
| «Мона Лиза» | Rare | 4.8K |
| «Золотой трон» | Epic | 5.6K |
| «Царь-смерч» | Legendary | 357K |
| Secret (по D56; предметов ещё нет) | Secret | ≈ 1.1B |

Полная таблица — в `docs/TOWER_DECISIONS_DRAFT.md`.
